# Loom MVP 模块拆解与开发顺序 v0.1

## 1. 文档信息

- 项目名称：Loom
- 文档版本：v0.1
- 文档类型：MVP 模块拆解与开发顺序
- 目标阶段：MVP / 第一阶段开发落地
- 关联文档：
  - `loom-architecture-v0.1.md`
  - `loom-data-model-v0.1.md`

## 2. 文档目标

本文档用于将 Loom 的架构方案进一步拆解为可执行的 MVP 模块、开发阶段、依赖关系和验收标准，帮助项目按最小可行路径推进，而不是一次性实现完整系统。

文档的核心目标是回答四个问题：

- Loom 第一版到底做哪些模块
- 这些模块之间的依赖顺序是什么
- 哪些能力必须先做，哪些可以后补
- 每个阶段完成后应达到什么可用状态

## 3. MVP 范围重申

Loom v0.1 的 MVP 范围如下：

- 本地运行
- 通过页面配置 API 源和订阅源
- 后台定时轮询数据源
- 将消息标准化并去重
- 使用本地 LM Studio 做分类、翻译、摘要、重要性辅助判断
- 对重复或相似消息进行聚合
- 主页面按时间线展示聚合卡片
- 支持展开查看全部来源
- 展示重要性与热度
- 仅保留最近 7 天消息

不在当前 MVP 范围内的内容：

- 日报和周报
- 非结构化网页抓取
- 团队协作
- 复杂事件图谱
- 云端部署

## 4. 开发原则

### 4.1 先跑通主链路

优先保证以下主链路可跑通：

```text
来源配置
→ 拉取数据
→ 标准化
→ 入库
→ 前端展示
```

### 4.2 先稳定后智能

先保证：

- 本地运行稳定
- 数据模型正确
- 时间线可用

再增强：

- AI 分类
- 翻译
- 聚合
- 评分

### 4.3 先单点可用，再整体联调

每个阶段都应该产出一个能运行和验证的系统状态，而不是只完成若干孤立代码。

## 5. MVP 模块总览

建议将 Loom v0.1 拆成以下 8 个模块：

1. 本地应用基础骨架
2. 来源配置模块
3. 采集与调度模块
4. 标准化与入库模块
5. 实时时间线展示模块
6. AI 增强模块
7. 聚合与评分模块
8. 生命周期与系统状态模块

其中建议的依赖顺序为：

```text
1 → 2 → 3 → 4 → 5 → 6 → 7 → 8
```

但在实现时可做少量并行，例如前端基础页面和数据库初始化可以同步进行。

## 6. 模块拆解

## 6.1 模块一：本地应用基础骨架

### 目标

建立 Loom 的本地运行框架，为后续各模块提供统一的应用入口、配置加载、数据库连接和前后端通信基础。

### 范围

- 本地服务启动机制
- 前端应用基础壳
- 本地数据库初始化
- 基础路由
- 基础日志
- 环境配置加载

### 产出

- 应用能够在本地启动
- 前端页面可打开
- 数据库可初始化
- 前后端基础通信可用

### 依赖

- 无

### 验收标准

- 启动后可访问本地页面
- 能看到一个基础首页和健康检查状态
- 数据库初始化不会报错

## 6.2 模块二：来源配置模块

### 目标

让用户能够在页面中配置 API 和 Feed 来源，而不需要改代码。

### 范围

- Source 数据模型落地
- 来源列表页
- 新增来源
- 编辑来源
- 启用/停用来源
- 删除来源
- 测试连接

### 产出

- 完整的来源配置 UI
- 来源配置的本地持久化
- 测试连接能力

### 依赖

- 模块一

### 验收标准

- 能新增一个 API 来源
- 能新增一个 Feed 来源
- 能修改轮询频率与分类
- 能在页面上启停来源

## 6.3 模块三：采集与调度模块

### 目标

让 Loom 能够根据来源配置，定时抓取数据并处理失败重试。

### 范围

- Scheduler
- API Fetcher
- Feed Fetcher
- 重试与退避
- 网络状态检测
- 来源健康状态更新

### 产出

- 可按配置周期定时拉取来源
- 抓取结果可进入后续处理链路
- 失败可记录并显示

### 依赖

- 模块一
- 模块二

### 验收标准

- 配置好的来源会按周期执行
- 失败来源不会导致整个系统停止
- 最近成功时间与错误状态可查看

## 6.4 模块四：标准化与入库模块

### 目标

将来自不同来源的消息统一为标准 Message 模型，并完成基础去重和持久化。

### 范围

- 原始响应解析
- 标题和正文标准化
- 时间格式统一
- 链接标准化
- dedup_key 生成
- 基础去重
- 写入 Message 表

### 产出

- Message 入库能力
- 可查询最近消息
- 重复消息不会无限堆积

### 依赖

- 模块三

### 验收标准

- 至少支持两个不同结构来源写入同一 Message 模型
- 数据库中能查询到标准化结果
- 相同 external_id 或相同 URL 不会重复入库

## 6.5 模块五：实时时间线展示模块

### 目标

提供最小可用的主页面，让用户可以实时查看最新消息。

### 范围

- 时间线页面
- 新消息实时插入
- 基础卡片展示
- 原始链接跳转
- 分类筛选
- 来源筛选
- 搜索最近 7 天消息

### 初始实现建议

该阶段可先基于单条 Message 展示，等聚合模块完成后再升级为 Cluster 卡片展示。

### 产出

- 一个可实际使用的消息时间线
- 新消息可实时更新

### 依赖

- 模块四

### 验收标准

- 新抓取消息能在页面展示
- 可按时间排序
- 可点击原始链接
- 筛选条件可正常工作

## 6.6 模块六：AI 增强模块

### 目标

接入 LM Studio，为消息补充语言识别、英文中译、摘要、分类、标签和重要性辅助判断。

### 范围

- LM Studio 连接器
- Prompt 结构设计
- AI 调用队列或异步任务
- 语言识别
- 英文翻译
- 摘要生成
- 分类生成
- 标签提取
- AI 重要性辅助分

### 实现原则

- AI 增强不能阻塞主链路
- AI 失败时仍可展示原始消息
- 仅对有效消息触发 AI

### 产出

- Message 层的 AI 增强字段
- 系统状态页可看到 AI 服务状态

### 依赖

- 模块四
- 模块五

### 验收标准

- 英文消息可生成中文标题和摘要
- 消息可自动分配分类和标签
- LM Studio 不可用时系统仍可继续工作

## 6.7 模块七：聚合与评分模块

### 目标

将相似消息聚合为 Cluster 卡片，并为主页面提供重要性和热度。

### 范围

- Cluster 数据模型
- ClusterMessageMap 数据模型
- 相似度计算
- 聚合归组
- 代表消息选择
- Cluster 摘要生成
- importance_score 计算
- heat_score 计算
- 时间线从 Message 升级为 Cluster 展示
- 展开全部来源视图

### 实现策略

建议分两步：

#### 第一步：规则聚合

- 标题归一化
- 时间窗口匹配
- 分类匹配
- 简单文本相似度

#### 第二步：语义增强

- AI 摘要辅助
- embedding 或语义相似度增强
- 更稳定的归组判断

### 产出

- 主页面展示聚合卡片
- 重复信息收敛
- 用户可展开查看所有来源

### 依赖

- 模块四
- 模块六

### 验收标准

- 多条相似消息会被收敛为一张卡片
- 卡片展示来源数和消息数
- 能展开查看全部来源及原文链接
- 卡片可显示重要性与热度

## 6.8 模块八：生命周期与系统状态模块

### 目标

完善 Loom 的运营稳定性，包括 7 天清理、状态监控和系统运行可见性。

### 范围

- TTL 清理任务
- 启动时补偿清理
- Cluster 级联清理
- 系统状态页
- 网络状态展示
- 来源健康展示
- AI 服务状态展示
- 基础统计指标

### 产出

- 数据不会无上限增长
- 系统状态对用户透明可见

### 依赖

- 模块三
- 模块四
- 模块六
- 模块七

### 验收标准

- 7 天前消息会被自动删除
- 无有效消息的 Cluster 会被清理
- 页面可看到网络、来源、AI 状态

## 7. 推荐开发阶段

为了降低风险，建议按 4 个阶段推进。

## 7.1 阶段一：可运行骨架

包含模块：

- 模块一
- 模块二

阶段目标：

- 本地应用可启动
- 来源可通过页面配置

阶段结果：

- Loom 从“设计稿”变成“可运行壳”

## 7.2 阶段二：基础信息流跑通

包含模块：

- 模块三
- 模块四
- 模块五

阶段目标：

- 新消息能从来源进入数据库并展示在时间线上

阶段结果：

- Loom 成为一个基础可用的信息流工具

## 7.3 阶段三：AI 增强可用

包含模块：

- 模块六

阶段目标：

- 消息具备分类、中英对照、摘要和基础重要性辅助

阶段结果：

- Loom 从“数据流”升级为“AI 增强信息流”

## 7.4 阶段四：聚合与收敛

包含模块：

- 模块七
- 模块八

阶段目标：

- 重复消息聚合
- 热度和重要性稳定展示
- 生命周期和状态页完成

阶段结果：

- Loom 成为可长期使用的本地实时聚合终端

## 8. 每阶段的里程碑定义

## 8.1 里程碑 M1：本地壳可启动

用户可以：

- 打开 Loom
- 进入来源配置页
- 添加来源

## 8.2 里程碑 M2：消息能流进来

用户可以：

- 配置来源
- 等待自动轮询
- 在页面看到最新消息

## 8.3 里程碑 M3：消息具备 AI 理解能力

用户可以：

- 看到分类
- 看到中文翻译
- 看到摘要

## 8.4 里程碑 M4：重复信息被收敛

用户可以：

- 看到聚合卡片
- 展开全部来源
- 根据重要性和热度快速判断优先级

## 10. 开发优先级建议

## 10.1 P0

必须优先完成：

- 本地应用基础骨架
- 来源配置模块
- 采集与调度模块
- 标准化与入库模块
- 实时时间线展示模块

没有这些，Loom 还不能形成基本产品闭环。

## 10.2 P1

完成基础可用后优先补强：

- AI 增强模块
- 聚合与评分模块

这些决定 Loom 的产品差异化。

## 10.3 P2

最后补完稳定性和可维护性：

- 生命周期与系统状态模块

虽然重要，但不必阻塞最早期主链路验证。

## 11. 风险与应对

## 11.1 来源结构不稳定

风险：

- API 字段变化
- Feed 结构不一致

应对：

- 标准化层做适配器
- 来源配置支持测试和错误展示

## 11.2 AI 延迟影响体验

风险：

- LM Studio 响应较慢

应对：

- AI 异步执行
- 先展示基础消息，再补齐 AI 字段

## 11.3 聚合误判

风险：

- 不同事件被错误合并

应对：

- 初期聚合阈值设保守
- 无法确定时单独成组

## 11.4 本地长期运行稳定性

风险：

- 调度器卡住
- 断网恢复不完整

应对：

- 增加状态页
- 增加失败重试与最后成功时间展示

## 12. 推荐最小交付顺序

如果希望尽快看到可用成果，建议按以下顺序交付：

### 交付 1

- 本地应用壳
- 来源配置页

### 交付 2

- 轮询抓取
- 标准化入库
- 时间线页面

### 交付 3

- LM Studio 接入
- 分类、翻译、摘要

### 交付 4

- 聚合卡片
- 来源展开
- 重要性与热度

### 交付 5

- 7 天清理
- 系统状态页

这样做的好处是每次交付后都能实际使用，而不是长期停留在“内部能力建设”阶段。

## 13. 验收视角

从用户角度看，Loom MVP 完成时应该能够做到：

- 我能自己配置多个 API 和订阅源
- 应用在本地自动拉取消息
- 新消息能实时出现在主页面
- 英文消息会有中文对照
- 重复消息不会铺满页面，而是聚合成一张卡片
- 我能展开看到所有来源
- 我能看出哪些消息更重要，哪些更热
- 系统只保留最近 7 天消息

如果这 8 点都成立，则 Loom 的 MVP 已经具备清晰的产品价值。

## 14. 结论

Loom 的 MVP 不应一次性追求完整资讯平台，而应按“本地可用、主链路优先、AI 增强、聚合收敛、稳定运维”这条路径逐步推进。

建议的最优顺序是：

```text
基础骨架
→ 来源配置
→ 采集调度
→ 标准化入库
→ 时间线展示
→ AI 增强
→ 聚合与评分
→ 生命周期与系统状态
```

这条路径能够让 Loom 尽快从架构设计转化为一个真实可用、持续迭代的本地信息流产品。
