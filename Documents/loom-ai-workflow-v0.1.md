# Loom AI 工作流与 Prompt 设计 v0.1

## 1. 文档信息

- 项目名称：Loom
- 文档版本：v0.1
- 文档类型：AI 工作流与 Prompt 设计
- 目标阶段：MVP / 第一阶段落地
- 关联文档：
  - `loom-architecture-v0.1.md`
  - `loom-data-model-v0.1.md`
  - `loom-api-and-interaction-v0.1.md`

## 2. 文档目标

本文档用于明确 Loom 中 AI 的职责边界、调用时机、输出结构、失败降级策略和 Prompt 设计方向，确保 AI 在 MVP 阶段真正服务于信息流质量，而不是让系统被模型行为牵着走。

Loom 当前的 AI 来源为本地 LM Studio，因此设计重点是：

- 控制调用成本与延迟
- 让输出结构化、可落表
- 让失败可回退
- 让结果服务于聚合、分类、翻译和评分

## 3. AI 在 Loom 中的职责边界

## 3.1 AI 负责的事情

- 语言识别辅助
- 英文消息中文翻译
- 单条消息摘要
- 分类建议
- 标签提取
- 重要性辅助判断
- 聚合辅助判断

## 3.2 AI 不负责的事情

- 数据抓取
- 调度器运行
- 基础去重
- 时间排序
- 数据库存储
- WebSocket 推送
- 最终是否入库

## 3.3 设计原则

- Rule-first，AI-enhanced
- AI 结果是增强信息，不是唯一真相
- AI 不应阻塞主消息链路
- AI 输出必须结构化
- AI 失败必须能优雅降级

## 4. AI 工作流总览

对于每一条标准化后的 Message，推荐的处理流程如下：

```text
Message 标准化完成
→ 基础去重
→ 判断是否需要 AI 处理
→ 语言识别
→ 若为英文则翻译
→ 生成摘要
→ 生成分类与标签
→ 生成 AI 重要性辅助分
→ 回写 Message
→ 参与聚合与评分
```

## 5. AI 任务拆分

## 5.1 任务一：语言识别

### 目标

识别消息主要语言，输出 `zh`、`en`、`other` 或 `unknown`。

### 说明

如果标准库语言识别已经足够稳定，这一步可以优先交给规则或本地库处理，AI 仅在不确定时参与。

### 输出字段

- `language`

## 5.2 任务二：英文翻译

### 目标

为英文消息生成中文标题和中文摘要，满足中英对照需求。

### 输出字段

- `translated_title_zh`
- `translated_summary_zh`

### 说明

- 中文消息不强制翻译成英文
- 翻译要忠于原文，避免扩写和主观解读

## 5.3 任务三：摘要生成

### 目标

将原始消息压缩为简洁、信息密度高的摘要，便于时间线快速消费。

### 输出字段

- `ai_summary`

### 要求

- 尽量 1 到 3 句话
- 不要加入原文没有的信息
- 不要输出空泛判断

## 5.4 任务四：分类与标签

### 目标

为消息输出一个主分类和若干标签。

### 输出字段

- `primary_category`
- `tags_json`

### 分类范围建议

- 时政
- AI
- 科技
- 数字货币
- 金融
- 公司
- 宏观
- 安全
- 产品发布
- 其他

## 5.5 任务五：重要性辅助判断

### 目标

让 AI 输出一个 0–100 的辅助分以及简短理由，供评分模块融合。

### 输出字段

- `ai_importance_score`
- `ai_confidence`

### 说明

AI 不直接决定最终重要性，只提供补充信号。

## 5.6 任务六：聚合辅助判断

### 目标

在规则相似度不足以稳定判断时，辅助判断两条消息是否属于同一件事。

### 输入

- 候选消息 A
- 候选消息 B 或某个 Cluster 的代表摘要

### 输出

- `same_story`: true/false
- `confidence`: 0–1

### 说明

第一版可选，优先级低于翻译、分类和摘要。

## 6. AI 调用时机

## 6.1 推荐调用顺序

```text
标准化后
→ 规则判断是否需要 AI
→ 语言识别
→ 若英文则翻译
→ 摘要
→ 分类与标签
→ 重要性辅助分
```

## 6.2 为什么不建议一次大 Prompt 全做完

虽然一次调用返回全部字段看起来方便，但第一版更推荐“结构化组合任务”或“半组合任务”，原因是：

- 更容易调试
- 更容易回退单项失败
- 更容易针对英文消息只做必要动作
- 后续更容易优化成本

## 6.3 推荐折中方案

第一版可以把以下三项合并为一个调用：

- 摘要
- 分类
- 标签
- 重要性辅助分

把翻译单独作为另一个调用。

这样既减少调用次数，又便于处理英文特殊逻辑。

## 7. AI 触发策略

## 7.1 必须触发的情况

- 去重后保留的新英文消息
- 高重要性候选消息
- 需要聚合摘要的代表消息

## 7.2 可跳过的情况

- 明显重复消息
- 内容极短且信息量低
- 已有相同摘要结果的消息

## 7.3 异步处理建议

推荐以异步任务方式执行 AI：

- Message 先入库
- AI 状态标记为 pending
- AI 完成后回写字段
- 触发前端卡片刷新事件

这样可以保证主链路流畅。

## 8. Prompt 设计原则

Prompt 必须遵循以下原则：

- 输出结构固定
- 不允许自由散文回答
- 明确禁止编造
- 明确约束分类范围
- 明确要求摘要简洁
- 明确要求翻译忠实

## 9. 推荐输出格式

所有 AI 输出尽量统一为 JSON。

### 通用结构示例

```json
{
  "language": "en",
  "translated_title_zh": "推出 GPT-X",
  "ai_summary": "OpenAI announced a new model...",
  "translated_summary_zh": "OpenAI 发布了一款新模型...",
  "primary_category": "AI",
  "tags": ["模型发布", "OpenAI"],
  "ai_importance_score": 86,
  "ai_confidence": 0.87
}
```

## 10. Prompt 模板建议

## 10.1 翻译 Prompt

### 用途

- 英文消息生成中文标题和中文摘要

### 模板示例

```text
你是一个严格的信息翻译助手。

任务：
1. 将输入消息标题翻译成简洁准确的中文
2. 基于输入消息内容生成一段中文摘要

要求：
- 忠于原文，不要扩写
- 不要加入原文没有的信息
- 中文表达自然、简洁
- 摘要控制在 1 到 3 句话
- 只输出 JSON，不输出任何额外说明

输出格式：
{
  "translated_title_zh": "...",
  "translated_summary_zh": "..."
}

输入标题：
{{title}}

输入内容：
{{content}}
```

## 10.2 摘要 + 分类 + 标签 + 重要性 Prompt

### 模板示例

```text
你是一个信息流分析助手。

你的任务是基于输入消息，输出结构化分析结果。

要求：
- 不要编造输入中不存在的信息
- 主分类只能从以下选项中选择一个：
  时政、AI、科技、数字货币、金融、公司、宏观、安全、产品发布、其他
- 标签控制在 1 到 5 个
- 摘要控制在 1 到 3 句话
- 重要性分数范围是 0 到 100
- 只输出 JSON，不输出任何额外说明

输出格式：
{
  "ai_summary": "...",
  "primary_category": "...",
  "tags": ["..."],
  "ai_importance_score": 0,
  "ai_confidence": 0.0
}

输入标题：
{{title}}

输入内容：
{{content}}
```

## 10.3 聚合辅助 Prompt

### 模板示例

```text
你是一个信息聚合判断助手。

请判断下面两条消息是否在描述同一件事情。

要求：
- 如果明显不是同一件事，返回 false
- 如果只是同一主题但不是同一事件，也返回 false
- 只输出 JSON

输出格式：
{
  "same_story": true,
  "confidence": 0.0,
  "reason": "..."
}

消息A标题：
{{titleA}}

消息A摘要：
{{summaryA}}

消息B标题：
{{titleB}}

消息B摘要：
{{summaryB}}
```

## 11. AI 输出校验

AI 返回结果不能直接信任，必须做结构校验。

## 11.1 校验内容

- 是否为合法 JSON
- 必填字段是否存在
- 分类是否在允许范围内
- 分数是否在范围内
- tags 是否为数组

## 11.2 异常处理

若校验失败：

- 记录日志
- 标记 AI 任务失败
- 允许后续手动或自动重试

## 12. 降级策略

## 12.1 LM Studio 不可用

系统行为建议：

- 仍然保留消息抓取、入库、展示能力
- 仅缺失 AI 增强字段
- 时间线显示原始标题和来源
- 系统状态页提示 AI 不可用

## 12.2 翻译失败

- 英文消息先展示原文
- 标记“翻译处理中”或“翻译失败”
- 允许后续重试

## 12.3 分类失败

- 先使用来源默认分类或规则分类
- 无法判断时归入“其他”

## 12.4 摘要失败

- 前端可直接展示标题和来源
- 展开时查看原文链接

## 13. AI 与评分模块的关系

## 13.1 最终重要性不由 AI 单独决定

最终分数建议由以下两部分构成：

- 规则分
- AI 辅助分

示意：

```text
final_importance_score =
0.70 * rule_importance_score +
0.30 * ai_importance_score
```

或者：

```text
final_importance_score =
rule_importance_score + adjustment_from_ai
```

第一版建议保持简单和可解释。

## 13.2 热度不建议主要依赖 AI

热度更适合通过数据统计得出：

- message_count
- source_count
- recency_acceleration

AI 可辅助，但不应成为主来源。

## 14. AI 与聚合模块的关系

## 14.1 第一版推荐

聚合判断主要依靠：

- 标题相似
- 时间接近
- 分类一致
- 关键词或摘要相似

AI 仅在边界情况下辅助判断。

## 14.2 原因

如果一开始让 AI 主导聚合：

- 成本更高
- 行为更难解释
- 出错更难排查

因此第一版应优先采用规则聚合，AI 只用于提高边缘场景准确率。

## 15. AI 状态管理建议

建议为每条 Message 增加 AI 处理状态概念：

- pending
- processing
- success
- failed

即便这个状态不单独入主表，也建议在任务日志或运行态中存在。

## 16. 典型消息处理示例

## 16.1 英文消息

```text
抓取到英文消息
→ 标准化
→ 入库
→ 识别语言为 en
→ 翻译生成中文标题和摘要
→ 生成摘要、分类、标签、AI 重要性分
→ 回写消息表
→ 参与聚合
→ 更新前端卡片
```

## 16.2 中文消息

```text
抓取到中文消息
→ 标准化
→ 入库
→ 语言识别为 zh
→ 跳过翻译
→ 生成摘要、分类、标签、AI 重要性分
→ 回写消息表
→ 参与聚合
```

## 17. 推荐实现顺序

建议 AI 相关能力按以下顺序实现：

1. LM Studio 连接器
2. 语言识别
3. 英文中译
4. 摘要
5. 分类与标签
6. 重要性辅助分
7. 聚合辅助判断

这样能最快满足你最关心的中英对照和信息理解能力。

## 18. 结论

Loom v0.1 中 AI 的最佳角色是“增强层”，而不是“主控制层”。它应该重点承担：

- 英文中译
- 摘要压缩
- 分类与标签
- 重要性辅助判断

同时保持以下原则：

- 异步执行
- 结构化输出
- 失败可回退
- 不阻塞主链路
- 不替代规则系统

按照本文档设计，Loom 可以在本地 LM Studio 的基础上获得稳定、可解释、可落表的 AI 能力。
