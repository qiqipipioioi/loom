# Loom 架构设计文档 v0.1

## 1. 文档信息

- 项目名称：Loom
- 文档版本：v0.1
- 文档类型：架构设计文档
- 目标阶段：MVP / 第一阶段落地
- 适用范围：本地运行的个人实时信息流聚合系统

## 2. 项目背景

Loom 的目标是构建一个不依赖第三方资讯聚合平台的本地信息流系统，用于在个人电脑上持续接收、处理、聚合和展示来自 API 与订阅源的信息。

与传统资讯流产品不同，Loom 不以“尽可能多展示原始消息”为目标，而是以“更快发现重要信息、减少重复噪音、保留原始来源、提供 AI 辅助理解”为目标。系统将运行于本地机器，在联网且应用启动时工作，无需部署到服务器。

## 3. 设计目标

### 3.1 核心目标

- 支持配置化接入 API 源与订阅源
- 在本地机器上持续轮询并接收新消息
- 以时间线方式实时展示新消息
- 对多源重复消息进行聚合
- 支持展开查看聚合消息下的全部来源
- 对消息进行分类、重要性评分、热度评分
- 对英文消息提供中英文对照展示
- 所有消息仅保留 7 天，过期自动清理
- AI 能力通过本地 LM Studio 接口提供

### 3.2 产品目标

- 构建一个个人可控的信息流系统
- 降低重复信息和噪音带来的阅读成本
- 保留原始来源链路，提升信息可追溯性
- 让用户更快判断“这件事是否值得看、是否正在发酵”

## 4. 非目标

以下内容不属于当前版本范围：

- 非结构化网页抓取与正文解析
- 云端部署、多机同步、远程服务端架构
- 日报、周报、定时简报模块
- 复杂知识图谱与长期事件演化系统
- 多用户权限、团队协作
- 全量历史归档与长期冷存储
- 移动端原生应用优先支持

## 5. 需求概述

### 5.1 功能需求

- 数据源仅支持 API 和订阅源
- 数据源必须支持在页面中进行新增、编辑、启停和测试
- 应用运行于本地，开机联网且应用启动时工作
- 主页面按时间线实时展示推送消息
- 每条展示项必须提供原始链接
- 消息保存 7 天，超期自动清除
- 系统需要给出信息的重要性与热度
- 不包含日报模块
- AI 使用本地 LM Studio 接口
- 对消息进行分类，如时政、AI、科技、数字货币等
- 英文消息需提供中英文对照展示
- 多源重复消息需自动聚合，并支持展开查看全部消息源

### 5.2 非功能需求

- 本地运行稳定，不依赖远程服务端
- 轮询和展示延迟可控
- 配置化扩展新来源
- 模块职责清晰，可迭代增强
- AI 调用可选、可回退、不中断主链路
- 评分与聚合结果具备一定可解释性

## 6. 总体架构

### 6.1 架构原则

- Local-first：所有核心能力本地运行
- Config-first：来源通过配置接入，不依赖硬编码
- Timeline-first：主视图围绕实时信息时间线
- Rule-first, AI-enhanced：规则为主，AI 做增强
- Retention-bounded：仅保留 7 天，保持轻量
- Traceable：所有聚合结果可回溯到原始来源

### 6.2 总体架构图

```text
[Source Config UI]
  API Source / Feed Subscription 配置
        ↓
[Local Scheduler]
  定时轮询 / 重试 / 频率控制 / 健康检查
        ↓
[Ingestion Layer]
  API Fetcher / Feed Fetcher
        ↓
[Normalization Layer]
  字段统一 / 时间标准化 / 链接标准化 / 去重
        ↓
[Language & AI Layer]
  语言识别 / 英文翻译 / 分类 / 标签 / 摘要 / 重要性辅助评分
        ↓
[Clustering Layer]
  相似消息聚合 / 多源归组 / 聚合摘要更新
        ↓
[Scoring Layer]
  Importance Score / Heat Score
        ↓
[Storage Layer]
  SQLite + Full Text Search + 本地缓存
        ↓
[Realtime Delivery Layer]
  WebSocket / SSE
        ↓
[Frontend UI]
  实时时间线 / 聚合展开 / 分类筛选 / 来源管理 / 系统状态
```

## 7. 核心模块设计

### 7.1 Source Config 模块

#### 职责

- 管理 API 源与订阅源配置
- 提供页面化配置能力
- 提供启停、测试、频率控制、健康状态查看

#### 支持的来源类型

- API Source
- Feed Subscription（RSS/Atom 等）

#### 配置项建议

##### API Source

- 名称
- 请求地址
- 请求方法
- 请求头
- 认证信息
- 轮询频率
- 超时时间
- 数据提取规则
- 默认分类
- 是否启用

##### Feed Subscription

- 名称
- Feed URL
- 轮询频率
- 默认分类
- 是否启用

#### 输出

- 标准化的 Source 配置对象
- 可供调度器消费的任务定义

### 7.2 Local Scheduler 模块

#### 职责

- 周期性执行各来源抓取任务
- 处理失败重试和退避
- 控制不同来源的轮询频率
- 维护来源健康状态

#### 设计说明

由于 Loom 不采用分布式部署，调度器无需复杂分片，仅需本地稳定运行。建议每个来源对应一个逻辑任务，由统一调度器根据配置频率执行。

#### 关键能力

- 定时轮询
- 启动时恢复
- 断网检测
- 重试与失败记录
- 来源启停

### 7.3 Ingestion 模块

#### 职责

- 拉取原始数据
- 将不同来源的响应转换为原始消息集合
- 保留必要的抓取上下文

#### 子模块

- API Fetcher
- Feed Fetcher

#### 输入

- Source 配置
- 调度器触发任务

#### 输出

- Raw Message 列表

### 7.4 Normalization 模块

#### 职责

- 将不同来源的原始消息统一为标准消息结构
- 清洗无效字段
- 统一时间与链接格式
- 生成基础去重标识

#### 处理内容

- 标题抽取
- 正文抽取
- 来源映射
- 发布时间标准化
- URL 规范化
- external_id 提取
- dedup_key 生成

#### 输出

- 标准化后的 Message 对象

### 7.5 Language & AI 模块

#### 职责

- 识别消息语言
- 对英文内容生成中文对照版本
- 生成摘要、分类、标签
- 提供重要性辅助评分
- 为聚合提供语义辅助信号

#### AI 提供方式

- 本地 LM Studio API

#### AI 子能力

- Language Detect
- Translate EN → ZH
- Summarize
- Categorize
- Tag Extract
- Importance Assist
- Cluster Assist

#### 设计原则

- AI 不参与采集与调度
- AI 不负责基础去重与时间排序
- AI 结果为增强信息，可失败回退
- AI 调用应具备条件触发策略，避免对所有低价值消息全量处理

#### 条件调用建议

- 仅处理去重后保留的消息
- 英文消息优先触发翻译
- 信息长度过短可跳过摘要
- 疑似低价值或重复消息可降低处理优先级

### 7.6 Clustering 模块

#### 职责

- 对多源重复或相似消息进行聚合
- 将原始消息归入某个聚合组
- 支持主页面按聚合结果展示
- 支持展开查看全部消息源

#### 聚合目标

当前版本不构建长期事件知识图谱，仅做短期消息聚合，重点解决：

- 同一事件多源重复
- 同一时间窗口内高相似度消息合并
- 展示来源覆盖情况

#### 聚合依据

- 标题相似度
- 内容或摘要语义相似度
- 实体重叠
- 时间接近度
- 分类一致性

#### 输出

- Cluster / Story 对象
- Message 与 Cluster 的关联关系

### 7.7 Scoring 模块

#### 职责

- 计算消息或聚合组的重要性
- 计算聚合组的热度
- 输出前端展示用评分

#### 评分输出

- importance_score
- heat_score

#### 设计原则

- 重要性与热度分开定义
- 规则评分为主，AI 做校准
- 分值应可解释并支持后续调参

### 7.8 Storage 模块

#### 职责

- 存储来源配置、原始消息、聚合结果、AI 结果、评分结果
- 支持 7 天消息生命周期管理
- 提供前端查询与搜索能力

#### 存储建议

- SQLite：核心业务数据
- Full Text Search：文本搜索
- 本地缓存：UI 刷新与短期状态

#### 生命周期要求

- Message 仅保留 7 天
- Cluster 若无有效 Message 关联则删除
- AI 结果与映射数据同步清理

### 7.9 Realtime Delivery 模块

#### 职责

- 在新消息到达或聚合更新后，实时通知前端
- 支持时间线顶部插入新卡片
- 支持卡片热度、来源数等动态刷新

#### 技术形式

- WebSocket 或 SSE

### 7.10 Frontend UI 模块

#### 页面组成

- 实时时间线页面
- 来源配置页面
- 系统状态页面

#### 主页面职责

- 默认展示按时间排序的聚合消息卡片
- 支持展开查看全部来源
- 支持展示中英对照
- 支持分类、来源、时间、分数筛选

## 9. 数据处理流程

### 9.1 主处理链路

```text
来源配置加载
→ 调度器触发抓取
→ 拉取原始消息
→ 标准化
→ 基础去重
→ 语言识别
→ 英文翻译
→ 分类/标签/摘要
→ 聚合归组
→ 计算重要性与热度
→ 写入本地存储
→ 推送到前端时间线
```

### 9.2 去重与聚合关系

- 去重用于消除完全重复数据
- 聚合用于合并表达同一事件的多源消息
- 原始消息不因聚合而丢失
- 主页面展示聚合卡片，展开后展示所有来源

## 11. 英文中英对照设计

### 11.1 目标

对英文消息提供中英双语展示能力，提升信息消费效率。

### 11.2 处理策略

- 识别消息语言
- 若为英文，调用本地 LM Studio 生成中文标题与中文摘要
- 原文保留不变
- 中文消息不强制生成英文版本

### 11.3 展示策略

英文消息在 UI 中展示：

- 原始英文标题
- 中文标题
- 原始英文摘要
- 中文摘要

聚合卡片优先展示中文摘要，并支持查看英文原始内容。

## 12. 聚合设计

### 12.1 目标

将同一时间窗口内、指向同一事件的多条消息聚合为一张卡片，降低重复阅读成本，并保留全部来源供展开查看。

### 12.2 聚合输入

- 标题
- 摘要
- 标签
- 分类
- 时间
- 来源
- 实体信息
- 语义向量

### 12.3 相似度参考因子

- 标题相似
- 摘要语义相似
- 时间接近
- 实体重叠
- 分类一致

### 12.4 聚合输出

- 一个 Cluster 对应多条 Message
- 默认展示代表消息
- 支持展开查看来源清单

### 12.5 前端表现

卡片上展示：

- 聚合标题
- 热度
- 重要性
- 来源数
- 消息数
- 最新时间
- 原始链接
- 展开按钮

展开后展示：

- 全部来源列表
- 每个来源的标题、语言、发布时间、链接

## 13. 评分模型设计

### 13.1 重要性定义

重要性表示这条信息或这组信息是否值得优先关注，更偏向决策价值。

### 13.2 重要性影响因子

- 来源可信度
- 分类权重
- 关键词权重
- 是否命中重点关注对象
- 新颖性
- AI 辅助判断

### 13.3 推荐公式

```text
importance_score =
0.30 * source_score +
0.20 * category_weight +
0.20 * signal_keyword_weight +
0.15 * novelty_score +
0.15 * ai_importance_score
```

聚合卡片的重要性可结合代表消息和高可信来源进行加权。

### 13.4 热度定义

热度表示某个主题在短时间内被多少来源、多少消息提及，以及传播速度如何。

### 13.5 热度影响因子

- 聚合组消息数
- 不同来源数
- 短窗口增长速度
- 来源多样性

### 13.6 推荐公式

```text
heat_score =
0.35 * normalized_message_count +
0.35 * normalized_source_count +
0.20 * recency_acceleration +
0.10 * source_diversity
```

### 13.7 评分展示原则

- 重要性与热度并列显示
- 高重要性不等于高热度
- 高热度不等于高可信

## 14. 存储与生命周期管理

### 14.1 存储策略

- Source：长期保存
- Message：仅保存 7 天
- Cluster：随关联 Message 生命周期动态存在
- 评分与 AI 结果随 Message/Cluster 生命周期同步管理

### 14.2 清理策略

- 启动时执行一次过期清理
- 定时执行过期清理
- 删除 7 天前 Message
- 删除无有效 Message 的 Cluster
- 删除关联映射与搜索索引

### 14.3 边界规则

若 Cluster 创建时间较早，但最近仍有新 Message 加入，则保留 Cluster，仅删除过期 Message，并重新计算统计值与热度。

## 16. 容错与降级策略

### 16.1 网络异常

- 暂停抓取
- 保持本地展示可用
- 网络恢复后继续轮询

### 16.2 来源异常

- 单个来源失败不影响全局
- 记录错误并重试
- 前端显示来源健康状态

### 16.3 AI 异常

- LM Studio 不可用时，不中断主链路
- 可仅使用规则分类和基础评分
- 英文消息可先展示原文，中文对照缺失时标记为未生成

### 16.4 聚合异常

- 无法确定聚合关系时，优先单独成组
- 避免错误合并带来的信息污染

## 17. 安全与隐私

- 所有业务数据默认保存在本地
- 外部认证信息应本地安全存储
- 不依赖云端 AI 服务
- 原始链接与来源数据需完整保留
- 配置界面应避免明文暴露敏感认证字段

## 18. 技术选型建议

本节为建议，不构成强制限制。

- 本地 Web UI

### AI 接口建议

  - 翻译
  - 分类
  - 摘要
  - 标签
  - 重要性判断辅助

- 用户反馈参与排序优化
- 系统通知增强

## 20. 结论

Loom v0.1 的最佳架构不是传统服务器型资讯平台，而是一个本地运行、配置驱动、AI 增强的实时聚合信息终端。其核心价值在于：

- 用户自主配置来源
- 本地持续拉取并展示实时信息
- 对重复消息聚合而非简单丢弃
- 保留全部来源并支持展开查看
- 对英文消息提供中英对照
- 通过重要性与热度帮助用户判断优先级
- 用 7 天生命周期保持系统轻量

该架构在复杂度、可实现性和实际使用价值之间取得了较好的平衡，适合作为 Loom 的第一阶段正式蓝图。
